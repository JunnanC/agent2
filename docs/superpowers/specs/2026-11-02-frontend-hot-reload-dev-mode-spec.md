# 前端热更新开发模式 Spec

## 背景

当前项目的 `nginx` 服务在镜像构建阶段执行前端构建，并把三个门户的 `dist` 文件复制进 Nginx 镜像。修改 `frontend/` 源码后，运行中的 `http://student.localhost:8080`、`http://teacher.localhost:8080` 和 `http://admin.localhost:8080` 不会自动变化，必须重新构建并重建 Nginx 容器。

项目需要一个面向开发的本地入口，让前端源码修改可以通过 Vite 热更新立即反映到浏览器，同时继续复用当前 Docker Compose 提供的后端和数据服务。

## 目标

- 提供学生端、教师端、管理端三个前端开发服务器入口。
- 前端源码保存后，浏览器能够通过 HMR 或自动刷新看到更新。
- 开发服务器访问后端 API 时保留正确的门户 Host 和 Origin，使门户权限和路由行为与现有入口一致。
- 保留现有 Nginx 静态入口，继续用于构建验证和部署式测试。
- 提供清晰的启动、停止和访问说明，减少开发者误用静态入口的情况。

## 功能需求

- F1：系统提供单条命令启动后端 Compose 服务和三个前端开发服务器。
- F2：系统提供分别启动学生端、教师端、管理端的命令，支持只调试一个门户。
- F3：三个前端开发服务器使用当前 `frontend/` 源码目录，源码修改后无需重建 Nginx 镜像即可更新页面。
- F4：前端开发服务器代理 `/api`、`/files` 和 `/workspace` 请求到本地后端，并为每个门户设置对应的 Host、Origin 和 WebSocket 转发行为。
- F5：系统保留当前 `:8080` 静态入口，开发入口与静态入口使用不同端口，避免端口冲突和行为混淆。
- F6：启动失败时能明确报告端口被占用、Docker 服务未启动或 Node 依赖缺失等常见问题。

## 非功能需求

- N1：开发模式不得删除、重置或覆盖现有数据库卷和用户未提交代码。
- N2：开发模式不得改变生产式 Compose 服务的 API、数据模型和认证逻辑。
- N3：开发模式使用项目声明的 Node.js 24+；启动前检查 Node.js 主版本并给出可读错误。
- N4：开发模式的前端端口必须可通过环境变量覆盖。
- N5：文档和脚本应适用于 Windows PowerShell，并保留现有 Linux shell 入口的可选兼容性。

## 不做的事

- 不把 Vite 开发服务器作为生产部署方式。
- 不修改 Django、数据库迁移、认证账号或业务 API。
- 不自动修复与热更新无关的现有 ESLint、Vitest 或依赖审计问题。
- 不替换现有 Nginx 静态构建流程。

## 验收标准

- AC1：执行开发模式启动命令后，后端服务保持健康，三个前端开发服务器分别监听独立端口。
- AC2：打开三个开发入口可以看到对应门户页面，学生、教师、管理端页面标题和门户内容正确。
- AC3：修改任一门户的可见文本或样式并保存，浏览器在无需重建 Nginx 镜像的情况下显示修改结果。
- AC4：从每个开发入口发起 `/api/v2/health` 请求，后端返回 200，且响应中的门户标识分别为 `USER`、`TEACHING`、`PLATFORM`。
- AC5：学生端 `/workspace` WebSocket 代理仍可建立，教师端和管理端保持既有禁止访问约束。
- AC6：执行停止命令只停止本次开发模式启动的进程/容器，不删除数据库、Redis、MongoDB、MinIO 数据卷。
- AC7：静态入口 `http://*.localhost:8080` 仍可访问，重新构建 Nginx 后三个门户构建成功。
