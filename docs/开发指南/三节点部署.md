# 三节点 Compose 发布

A 负责网站、API 和普通任务，B 保留唯一的业务数据库及对象存储，C 负责工作区网关、运行与存储 worker。生产 Runner 只保留在 B。原单机 CD 在检测到 `/etc/agent2-cd/topology.json` 后，转交 `scripts/cd/deploy-three-node.py`。

## 首次接入

先完成网络、镜像和业务验证，再切换正式队列。不能把尚未验收的节点直接放入生产消费组。当前网络使用 SSH 加密的独立点对点隧道，A/B 的 `10.253.70.0/30` 与 B/C 的 `10.253.72.0/30` 互通；工作区 overlay 为 `10.253.71.0/24`，数据 overlay 为 `10.253.73.0/24`。B 到 C 的回包需以 Swarm 中声明的 `10.253.70.2` 为源地址。Docker API 只通过受限桥接地址和 SSH 转发访问。

使用已验证的旧 Compose 配置在 B 上生成私有的 resolved JSON，再运行 `render-node-role.py --role A|B|C INPUT OUTPUT`。输入、输出都包含生产凭证，只留在服务器，权限为 0600。生成器要求已有数据卷显式标记为 external，删除跨角色 depends_on，并把迁移和授权容器放入 maintenance profile，避免普通启动隐式启动另一台机器的数据库。

把各节点的结果保存为 `/etc/agent2-cd/role.production.compose.json`。工作区 secret 保存在各节点 `/etc/agent2-cd/secrets/workspace_upstream_token`。网络及所有外部数据卷必须已存在；发布器不创建空库，也不清理历史卷和镜像。

C 可使用 `--staging` 生成隔离的 `*_c_check` 队列。A 的候选普通 worker 也应使用独立队列。切换时先停止旧消费者接单并等活动、预取及延时任务排空，再启用 A/C 的正式消费者；迁移期间同步修改开机恢复清单，防止 B 在重启后恢复已退役的 worker。

历史适配器保留原主机身份：`runtime/local-docker` 始终对应 A，`runtime/remote-121-43-28-192` 始终对应 B；C 使用独立的 `runtime/remote-47-96-228-53`。各节点通过不同 transport 地址访问相同主机，不修改历史任务冻结的 config_ref。发布器也保留这些配置内的固定工作区镜像；新工作区镜像的推广需单独完成目录和模板版本验证。

## 发布协调配置

`topology.json` 包含 `phase: active` 和 `nodes` 三项 A/B/C。每项包含已经核对过的 `expected_hostname` 及 `ssh` 参数数组。B 的数组必须为空，表示发布进程就在唯一的数据节点上；A/C 使用 B 上的专用部署密钥、固定 known_hosts 和 BatchMode，不复用个人密码。

首次切换前可把配置保存在 `topology.prepared.json` 并设置 `phase: prepared`，通过 `AGENT2_TOPOLOGY_FILE` 指向它。该状态允许预检，禁止正式发布。预检检查三个真实主机身份、角色清单、已有卷、服务健康和 worker 的 broker 控制响应，并确认 A 的旧数据库保持停用；不会拉镜像、运行迁移或修改服务。

## 每次正式发布

沿用四镜像构建和同一个生产发布锁。发布器确认 checkout 对应完整 RELEASE_SHA，随后在 B 登录镜像仓库、拉取目标镜像并固定完整 image ID，通过 SSH 分发 A/C 所需镜像并逐一比对。临时仓库凭证在分发前清除。三节点各自准备同一版本的 release 和私有角色配置。

发布器在 B 制作 MySQL 事务备份并检查 gzip 完整性，然后暂停 A/C worker 接单并等待任务排空。超时会恢复已暂停消费者并终止发布；不会为了发布强制杀死忙碌任务。之后停止 A API 和相关 worker，在 B 准备数据库用户，在 A 执行迁移，再由 B 授权。B 的数据库、Redis、MongoDB、MinIO 和扫描服务继续使用现有容器和数据卷。

按 B 日志、A API、C 网关及运行服务、A 普通 worker 和入口的顺序启动服务。A 的 Kong 指向 `workspace-gateway-c`；跨角色地址由私有数据 overlay 提供。三个门户健康入口及 A API、B 日志、C worker/网关的 GIT_REVISION 全部一致后，才更新三台的 current 指针与持久角色配置。

迁移开始后的失败需要人工恢复：旧应用镜像不能回退数据库结构。若数据库已有新写入，也不能启动 A 的历史数据库当作回滚。保留 B 为唯一数据源，先核对备份、schema 和应用版本，再决定如何恢复。

## 仍需独立验收

发布预检和容器健康不替代登录、终端 WebSocket、工作区运行、报告提交、教师评分和容量验收。物理健康探测覆盖人工预算的问题尚需改造；预算上限落实前保持 beat、周期容量探测和额外监控关闭。4 个 500m/768MiB 工作区与 1 个评测并发是初始验证目标，不能仅凭物理内存大小承诺容量。
