# 后端开发

> 核对日期：2026-11-05。唯一 Django 项目位于 `backend/`。返回[文档索引](../README.md)。

## 目录与依赖

`manage.py` 位于 backend 根目录，业务应用在 `apps/`，配置和 ASGI 入口在 `education_experiment_platform/`。

当前项目要求 Python 3.14；声明的主要版本为 Django 6.1.1、DRF 3.18.1、Celery 5.6.3。准确依赖以 [pyproject.toml](../../backend/pyproject.toml)、[uv.lock](../../backend/uv.lock)及 [requirements](../../backend/requirements/) 为准，不另维护一套版本冻结表。镜像直接使用 requirements 文件；修改依赖时同时核对声明、锁文件和镜像安装入口。

定时任务使用 Celery beat 和项目调度配置，不从早期文档添加未被当前依赖锁采用的调度扩展。

## 主机开发

下面的 uv 命令在 `backend/` 执行，使用已安装的 Python 3.14：

```powershell
uv sync --locked --extra dev
$env:DJANGO_SETTINGS_MODULE = "education_experiment_platform.settings.test"
uv run --no-sync python manage.py check
uv run --no-sync python manage.py makemigrations --check --dry-run
uv run --no-sync python -m pytest
uv run --no-sync python -m ruff check apps education_experiment_platform --exclude migrations --force-exclude
uv run --no-sync python -m mypy apps education_experiment_platform
```

已有合适虚拟环境时可直接使用对应 Python。测试设置使用内存 SQLite 和模拟运行时；不能把单测结果当作 MySQL 事务、真实 Docker 或 Swarm 验收。

从仓库根目录可执行 `./scripts/verify/backend-local.ps1`，它会查找 Python 3.14 及开发依赖，执行 Django、迁移、pytest、Schema、Ruff、mypy 和 Compose 配置检查，不启动完整业务环境。

## 本地服务与数据库

- 本地应用采用 `education_experiment_platform.settings.local` 和 MySQL；测试使用 `settings.test`，生产设置见同目录配置。
- 配置模板统一为根目录 [.env.example](../../.env.example)。本地 `.env`、密钥文件和覆盖配置不提交。
- 初次部署由 Compose 的迁移、账号授权等初始化服务准备数据库；既有数据环境变更前先确认项目、备份和迁移状态。
- 在容器执行管理命令可用 `docker compose exec django python manage.py <命令>`；后台调度与 Docker 操作由对应 Worker 执行。
- 新结构变更提交新迁移；不要修改已经执行的迁移名，不直接删除版本化业务行或追加型审计记录。

## 注册与管理员账号

学生、教师分别在各自门户注册。注册请求发送 24 小时有效的邮箱验证链接；验证前不创建账号。学生验证成功即可登录学生端。教师验证成功后资格为 `PENDING`，管理员在管理端审核通过后才能登录教师端；自行注册的教师账号不能进入学生端。注册接口按 IP 和邮箱限流，重复邮箱请求统一返回受理结果。

部署时配置 `EMAIL_HOST`、`EMAIL_PORT`、`EMAIL_HOST_USER`、`EMAIL_HOST_PASSWORD`、`EMAIL_USE_TLS`、`DEFAULT_FROM_EMAIL`；`EMAIL_BACKEND` 应为 SMTP 后端。`STUDENT_PUBLIC_URL` 和 `TEACHER_PUBLIC_URL` 必须是用户可访问的完整门户根地址，例如 `https://student.example.edu`。SMTP 凭据保存在部署密钥配置中。未配置 SMTP 主机时注册返回 503。仅在本地开发时可将 `EMAIL_BACKEND` 设为 `django.core.mail.backends.console.EmailBackend`，从 Django 日志读取验证链接。

首个管理员继续用 `bootstrap_platform_admin` 创建。后续只有服务器运维能运行 `add_platform_admin` 授予管理员资格；管理端没有授予入口。已有有效账号的示例：

```sh
docker compose exec django python manage.py add_platform_admin \
  --email existing@example.edu --reason '已核实的运维申请单号'
```

新建账号并授权时，再提供 `--username`、`--display-name`，用 `PLATFORM_ADMIN_BOOTSTRAP_PASSWORD` 环境变量传入初始密码。命令会写入密码哈希、审计和事件，不直接操作 MySQL 表。

## 代码修改边界

- 查询集中在 selector，业务写入由 service 负责；视图解析请求、鉴权并调用服务，不能绕过并发和状态规则。
- 结构更新检查事务、锁、唯一约束、审计与 Outbox；重试场景同时检查幂等。
- 模板、快照和成果变更要核对对象归属、扫描状态、摘要与保留期。
- 身份、课程能力、门户上下文与机器认证分别处理，不以页面角色判断替代对象授权。
- 真实本地运行时使用 opt-in 测试及专用环境；用例入口和 Docker 前提见[工作区运行时](算法工作区镜像.md)。

## 接口、种子与 CI

修改接口后运行 `./scripts/dev/export-openapi.ps1`，更新前端 OpenAPI、生成类型及调用端，并执行相关回归。

管理命令按功能命名，例如 `seed_accounts_e2e`、`seed_simulated_experiment`、`seed_real_workspace_e2e`。种子、重置和验收清理只用于明确可丢弃或精确授权的测试数据；不能对真实业务库批量重建。

CI 的实际配置见 [ci.yml](../../.github/workflows/ci.yml)：依赖锁校验、Ruff、后端单测，以及后端、Web、工作区、参考镜像构建。前端 lint、类型、单测及完整浏览器旅程仍需按[前端指南](../frontend/frontend-backend-integration-guide.md)执行；不因 CI 配置存在而宣称当前工作树已通过。
