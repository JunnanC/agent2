# 本地开发与最终真实部署约定

> 适用范围：平台基座-真实运行环境 的开发、测试、阶段记录与最终部署。  
> 生效日期：2026-09-20。  
> 本文是执行调度约定，不修改 `docs/架构设计/00-08` 中的架构、业务规则、安全边界和验收标准。

## 一、执行决定

在真实服务器、正式 DNS/TLS、镜像仓库和外部持久化服务具备之前，项目先使用本机 Docker Compose 环境按 平台基座-分析与集成 的既定顺序开发和测试。真实 Docker Swarm/VM 适配、HA、故障恢复和生产候选环境全链路验收集中在最终部署窗口完成，并按 真实运行环境 收口。

本地环境是集成测试环境，不是生产环境，也不用于声明高可用、容灾、正式安全边界或生产性能已经通过。

## 二、双门禁和状态定义

每个阶段分别记录开发门禁与发布门禁，状态只允许使用以下定义：

| 状态 | 含义 | 是否允许进入下一阶段 | 是否允许发布 |
|---|---|---:|---:|
| 未开始 | 尚未进入当前阶段 | 否 | 否 |
| 本地验证中 | 正在本机实现或测试 | 否 | 否 |
| 本地通过（真实环境待验收） | 本地 Definition of Done 已满足，真实环境项目仍为阻塞项 | 是，可进入下一阶段的本地工作 | 否 |
| 正式通过 | 本地证据和适用的真实环境证据均已完成 | 是 | 是 |

执行规则如下：

1. 平台基座 本地基座通过后，可以进入 共享基础设施 的本地实现与测试。
2. 共享基础设施-分析与集成 仍严格串行；前一阶段未达到“本地通过”时，不进入下一阶段。
3. 后续阶段必须调用前一阶段的真实本地 API 和数据库事实，不得用 Mock 绕过前置能力。
4. 实验环境装载/归档与回收 文档明确要求的 `FakeRuntime` 是架构规定的阶段性交付，不视为绕过依赖；真实 Runtime 由 真实运行环境 验收。
5. 只完成本地测试的阶段不得写成“正式通过”“生产就绪”或“已完成 HA”。
6. 真实环境到位后，必须先补齐 平台基座 基础设施验收，再完成 共享基础设施-分析与集成 的部署复验和 真实运行环境 全链路验收，才能进入发布评审。

## 三、本地开发环境

本地使用 `docker-compose.dev.yml` 提供可重复创建的真实依赖：

| 能力 | 本地实现 | 本地可验证范围 |
|---|---|---|
| Web 入口 | Nginx + Kong | 三门户 Host、机器 API 隔离、可信上下文覆盖、限流/超时配置、SSE |
| 后端 | Django + Celery | API、事务、权限、异步任务、健康检查、OpenAPI |
| 业务数据库 | MySQL 8.4 LTS | schema、约束、索引、迁移、事务、锁与并发 |
| 缓存/队列 | Redis | 缓存、Celery Broker/Result Backend、失败恢复 |
| 运行日志 | Fluent Bit + log-ingest + MongoDB Replica Set | 结构化日志、脱敏、TTL、日志服务中断隔离 |
| 对象存储 | MinIO | 上传、版本控制、校验和本地恢复测试 |
| 文件扫描 | ClamAV | 上传扫描链路和失败路径 |
| 观测 | OTel Collector + Prometheus | trace/metrics 配置与采集入口 |
| 三端前端 | user/teacher/admin 独立应用 | 真实 API、状态页面、构建、组件测试与 Playwright |

本地验证至少包含当前阶段文档要求的 schema、API、权限、幂等、并发、失败补偿、日志、OpenAPI、前端状态和 E2E。所有入口测试应优先经过 Nginx → Kong → Django，不得只访问 Django 容器。

## 四、配置与代码约束

- `.env` 仅保存本机开发值并保持 Git 忽略；不得把真实密码、Token、证书或私钥提交到仓库。
- `.env.example` 只维护变量名称、安全占位值和非敏感默认值。
- 域名、IP、端口、凭证、镜像仓库、存储地址和节点名不得写死在业务代码中。
- 生产配置通过环境变量、Swarm Secrets 和版本化 Configs 注入；密钥不得进入 Config、镜像、日志或命令历史。
- 本地与真实环境使用同一套业务 schema、OpenAPI 和业务规则；环境差异只能位于 settings、adapter 和基础设施配置边界。
- 外部 I/O 必须通过既定 adapter/service 边界，确保最终部署时替换连接参数或运行时适配器不改写业务状态机。
- 本地测试数据必须由独立 seed/factory 创建且可清理，不得作为生产初始化数据。

## 五、本地无法替代的验收

以下内容只能记录为“真实环境待验收”，不能由 Docker Desktop 的结果代替：

- 三 Manager quorum、Manager/Worker/Edge/Data 节点丢失与重新调度。
- 正式 DNS、TLS 证书链、入口负载均衡、防火墙和可信代理网段。
- 私有镜像仓库的构建、推送、鉴权、拉取和版本回滚。
- 外部 MySQL、Redis、MongoDB Replica Set、MinIO/S3 的冗余、备份、故障切换和恢复。
- Swarm Secrets/Configs 轮换、节点最小权限和真实 Runtime 网络隔离。
- 滚动升级失败后的自动回滚以及跨节点日志/指标连续性。
- 接近生产数据量下的性能、容量、RPO/RTO 和连续可用性指标。

## 六、最终真实部署顺序

1. 冻结待部署版本、OpenAPI revision、数据库 migration 和镜像 digest。
2. 收集并复核三台 Manager、节点角色、DNS/TLS、镜像仓库、网络 CIDR 和外部数据服务信息。
3. 创建生产候选环境的版本化 Configs 与 Secrets，不复用本地 `.env` 密钥。
4. 初始化三 Manager Swarm、应用节点标签并部署 平台基座 无状态基础服务。
5. 完成 平台基座 的入口、TLS、日志、外部存储、节点故障和滚动回滚验收，补齐 平台基座 出口证据。
6. 按 共享基础设施-分析与集成 的顺序执行 migration、seed、后端、Worker 和三端部署复验，不跳过任何失败阶段。
7. 执行 真实运行环境 的真实 Runtime、HA、恢复、性能、安全和完整业务旅程验收。
8. 所有阻塞项关闭后，把相应出口记录从“本地通过（真实环境待验收）”更新为“正式通过”，再进入发布评审。

## 七、阶段记录要求

每个 Pxx 出口记录必须额外包含：

```text
开发环境：本地 Compose / 真实预发布
本地门禁：未开始 / 验证中 / 通过
真实环境门禁：不适用 / 待验收 / 通过
本地证据：命令、测试数量、关键结果
真实环境阻塞：节点、DNS/TLS、存储、Runtime、HA、恢复、性能等
出口结论：本地通过（真实环境待验收） / 正式通过 / 未通过
```

真实环境证据至少记录执行时间、部署版本、环境标识、命令或测试用例、结果和可追溯日志位置。任何占位值、静态配置检查或单机结果都不能作为真实环境通过证据。
