# 真实工作区镜像与快照隔离改造总纲

> 状态：规划基线，供后续代码修改使用  
> 上游：真实运行环境 本地 Docker 真实适配、实验工作台改造  
> 环境约束：所有构建、测试和验收均在 Docker/Compose/Swarm 中执行，宿主机 Python、Node 和依赖不构成有效证据

## 一、目标

把当前工作区契约占位页替换为真实可编辑的 WebIDE，并将环境、在线文件和持久快照分离：

- 工作区镜像只包含 code-server、语言工具链和受控入口服务。
- 每个实验任务使用独立的工作区 Volume 保存在线编辑状态。
- 独立的 `workspace-storage-worker` 负责初始化、捕获、恢复和最终同步。
- MinIO 中的不可变 `WorkspaceSnapshot` 是测试、提交、检查点和归档使用的持久事实。
- 本地使用 `DOCKER_LOCAL` 完成全链路验证后，把同一 OCI 镜像按 digest 晋级到服务器 `DOCKER_SWARM`。
- 不修改现有 FakeRuntime 的测试语义，不原地改变已经分配任务冻结的运行时事实。

本阶段第一版只支持 Python 单文件 `main.py` 和 `webide` 能力。多文件工程、独立 Notebook、独立 Terminal、Preview 和用户自行构建 OCI 镜像均不在第一版范围内。

## 二、术语与边界

### 2.1 环境镜像

环境镜像是不可变 OCI 镜像，包含：

- 固定版本的 code-server。
- Python 和模板允许使用的依赖。
- 8080 端口的内部工作区路由器。
- `/healthz` 和 `/webide/` 契约。
- 必需的启动脚本和只读配置。

环境镜像不得包含任何具体学生、任务、课程、Session 或用户源文件。运行中的工作区容器不得通过 `docker commit` 生成新镜像。

### 2.2 在线工作区

在线工作区是任务专属 Docker Volume，挂载到工作区容器的 `/workspace`：

- 保存用户当前编辑的 `main.py`。
- 只允许该任务的工作区容器和受控存储作业挂载。
- 是短期在线状态，不是长期事实源。
- 容器重建时可以从最近的 MinIO 快照恢复。

### 2.3 工作区快照

工作区快照是扫描、校验并写入 MinIO 的不可变对象，继续使用现有 `ObjectAsset` 和 `WorkspaceSnapshot` 表达：

- 自动测试只读取明确关联的快照。
- 报告、成果、审核和归档只引用不可变快照或其执行证据。
- 检查点是对快照的命名引用；恢复必须同时恢复在线 Volume，不能只新增数据库引用。

本文中的“临时镜像”统一称为“工作区快照”。若未来允许学生执行 `docker build` 生成真正 OCI 镜像，必须另建 rootless BuildKit 和临时 Registry 方案，不得复用本阶段的快照链路。

### 2.4 存储 Worker

`workspace-storage-worker` 是独立平台服务，负责工作区存储作业，但自身不保存长期数据：

- 只从数据库接收作业 ID，不接收浏览器提供的容器 ID、Volume 名称或对象存储地址。
- 根据受管实例事实解析容器和 Volume。
- 执行初始化、捕获、恢复和最终同步。
- 把对象写入 MinIO，并通过 service 层提交数据库事实。
- 失败进入稳定错误状态和补偿流程。

## 三、当前基线与缺口

当前已有能力：

- `DockerLocalAdapter` 会创建任务专属命名 Volume，并挂载到 `/workspace`。
- 工作区容器不发布宿主机端口，通过 `workspace-gateway` 访问。
- `WorkspaceSession` 提供短期 token、HttpOnly Cookie、能力范围和续签。
- `WorkspaceSnapshot`、检查点、执行记录、MinIO 资产、审计和 Outbox 已存在。
- `RUN_CHECK` 已使用明确的快照资产创建一次性 judge 容器。
- 工作区网关已支持 HTTP、WebSocket、同源检查和 Session 权限校验。

当前缺口：

- `runtime/reference-workspace` 和 `runtime/algorithm-workspace` 都只返回契约占位页。
- 用户编辑内容来自前端 textarea，不来自容器 `/workspace`。
- 浏览器上传的单文件快照与真实 IDE 文件系统没有关联。
- 检查点恢复只创建新的数据库快照引用，不会写回工作区 Volume。
- FakeRuntime 任务共享参考端点，不能作为真实 WebIDE 验收。
- 任务容器共享 runtime 网络；真实终端启用后必须阻断跨任务横向访问。
- 当前 Swarm 工作区没有明确的跨节点 Volume 与恢复方案。
- 教师端模板创建目前默认声明多项能力，即使对应运行时未真实提供。

## 四、架构决策

### 4.1 构建一次、按 digest 晋级

真实工作区镜像只构建一次：

```text
工作区源码
  -> 构建 OCI 镜像
  -> 本地 DOCKER_LOCAL 验证
  -> 推送私有 Registry
  -> 锁定 sha256 manifest digest
  -> 本地按 digest 复验
  -> 服务器 DOCKER_SWARM 使用同一 digest
```

服务器阶段不得重新构建“等价镜像”。镜像 tag 仅用于展示，发布、模板和任务事实必须使用 digest。

### 4.2 容器与数据分离

```text
不可变环境镜像
  -> workspace-runtime 容器
       |- rootfs: read-only
       |- /tmp、/run: tmpfs
       |- /workspace: task-scoped Volume (rw)
       `- :8080 internal router

workspace-storage-worker
  -> 读取或恢复受管 Volume
  -> ClamAV / 大小 / 路径 / 文件类型校验
  -> MinIO immutable object
  -> ObjectAsset + WorkspaceSnapshot
```

不采用 data-only container。容器可负责处理数据，但 Volume 和 MinIO 才是存储载体。

### 4.3 双层状态

平台必须区分：

- `online workspace state`：Volume 中正在变化的文件。
- `durable snapshot state`：MinIO 中已确认的不可变版本。

前端只能显示“最后同步版本”，不能在没有编辑器集成协议的情况下声称 IDE 内容已经自动保存。

### 4.4 先单文件、后多文件

第一版只捕获 `/workspace/main.py`：

- 避免在没有一致性协议时直接打包一个持续变化的目录。
- 与现有 Python 单文件 judge 和 `execution_spec.entrypoint` 保持一致。
- 为后续目录归档保留数据模型扩展空间。

多文件支持必须单独设计文件清单、原子捕获、软链接、权限位、压缩炸弹和总容量规则。

### 4.5 旧任务不可变

已分配任务继续使用其冻结的 adapter、镜像和模板版本：

- 现有 FakeRuntime/实验工作台 任务不转换为真实工作区。
- 新建镜像、Runtime Adapter、模板版本和实验发布进行验证。
- 回滚通过停止新发布并恢复上一模板版本完成，不篡改历史任务。

## 五、目标组件

### 5.1 真实工作区镜像

建议新增或重构：

```text
runtime/algorithm-workspace/
|- Dockerfile
|- entrypoint.sh
|- router.conf 或等价内部路由配置
|- healthcheck
`- README.md
```

第一版镜像要求：

- 基础镜像和 code-server 版本固定，最终记录镜像 digest。
- 以专用非 root 用户运行。
- code-server 只监听容器回环地址，由内部路由器在 8080 暴露 `/webide/`。
- code-server 自身认证关闭，但 `/webide/` 必须由内部路由器验证实例级上游 token。
- 关闭遥测、更新检查和未经批准的扩展安装。
- 默认工作目录为 `/workspace`，入口文件为 `/workspace/main.py`。
- HOME、XDG 配置和缓存明确落到只读配置、任务 Volume 或受限 tmpfs，不得隐式写入根文件系统。
- `/healthz` 不包含敏感信息，仅表示路由器和 code-server 是否就绪。
- 不设置宿主机端口映射。

第一版 `workspace_capabilities`：

```json
{
  "require_gateway": true,
  "webide": true,
  "notebook": false,
  "terminal": false,
  "preview": false,
  "snapshot": true,
  "checkpoint": true
}
```

code-server 自带终端能力属于 WebIDE 内部能力，不等同于平台独立 `/terminal/` capability。

### 5.2 实例级上游鉴权

workspace-gateway 已验证用户 Session 和 workspace token，但真实工作区还必须验证请求确实来自网关。

建议使用每实例派生 token：

```text
upstream_token = HMAC(
  WORKSPACE_UPSTREAM_HMAC_KEY,
  instance.public_id | task.public_id | spec_digest
)
```

要求：

- runtime-worker 在创建容器时通过只读 secret 文件注入本实例 token。
- Django 内部授权接口在权限校验成功后把本实例 token只返回给 workspace-gateway。
- workspace-gateway 在 HTTP 和 WebSocket 上游握手中注入 `X-Workspace-Upstream-Token`。
- 内部路由器使用常量时间比较验证 token，并在转发到 code-server 前删除该头。
- 浏览器响应、日志、SSE、Outbox 和审计中不得出现 token。
- 一个任务容器读到自己的 token 后，也不能访问其他任务容器。
- 不得使用全局 `WORKSPACE_INTERNAL_KEY` 作为所有任务共用的上游 token。

网关只接受数据库中受管实例的 `http://tasks.<service>:<port>` 地址，继续禁止用户名、密码、任意路径和外部 Host。

### 5.3 工作区 Volume

Volume 命名仍由 Runtime Adapter 生成，业务请求不得传入名称。Volume 必须带有：

- `edu.platform.managed=true`
- `edu.platform.kind=volume`
- task、student、config_ref、expires_at 标签
- 可选的 snapshot lineage 和 storage generation

生命周期：

```text
创建 Volume
  -> 初始化 starter asset
  -> 挂载 workspace-runtime
  -> 用户编辑
  -> 多次捕获快照
  -> 最终同步
  -> 撤销 Session
  -> 销毁 runtime
  -> 保留短暂恢复窗口
  -> 删除 Volume
```

初始化必须由 Worker 从已扫描、ACTIVE、owner/purpose 匹配的 starter asset 产生。归档解包必须拒绝绝对路径、`..`、设备文件、FIFO、越界软链接和超限内容。

### 5.4 存储作业模型

建议新增 `WorkspaceStorageJob(VersionedModel)`，归属 `workspaces` app：

| 字段 | 说明 |
|---|---|
| `public_id` | ULID |
| `kind` | `INITIALIZE/CAPTURE/RESTORE/FINALIZE` |
| `task/session/instance` | 对象范围 |
| `source_snapshot` | RESTORE 的输入，可空 |
| `result_snapshot` | CAPTURE 的结果，可空 |
| `status` | `QUEUED/RUNNING/PASSED/FAILED/CANCELLED` |
| `client_seq/base_version` | 并发与顺序控制 |
| `idempotency_key/request_digest` | 幂等事实 |
| `failure_record` | 脱敏失败事实 |
| `trace_id` | 请求与异步链路关联 |
| `queued_at/started_at/completed_at` | 生命周期时间 |
| `row_version` | CAS |

约束建议：

- 同一 task/client_seq 的 CAPTURE 唯一。
- 同一 session 同时最多一个活动 CAPTURE 或 RESTORE。
- PASSED CAPTURE 必须有 `result_snapshot`。
- PASSED RESTORE 必须有 `source_snapshot`。
- 作业进入终态后不可重新写为运行态。

不要把容器 ID、Volume 名称、MinIO object key 或上游 token 放进公开 serializer。

### 5.5 Runtime Adapter 扩展

在 `apps/provisioning/ports.py` 增加明确端口，不复用目前只返回字符串的 `snapshot()`：

```python
class RuntimeAdapter(Protocol):
    def capture_workspace(
        self,
        *,
        external_id: str,
        relative_path: str,
        max_bytes: int,
    ) -> RuntimeWorkspaceArtifact: ...

    def restore_workspace(
        self,
        *,
        external_id: str,
        relative_path: str,
        content: bytes,
        expected_digest: str,
    ) -> None: ...
```

`RuntimeWorkspaceArtifact` 至少包含内容流、大小、digest、media type 和相对路径。不得返回宿主机绝对路径。

实现要求：

- `DockerLocalAdapter` 只操作带正确 managed/task 标签的实例。
- 捕获 `/workspace/main.py`，读取前后校验实例仍属于当前任务且状态可用。
- 恢复使用临时文件加原子 rename，避免半写入。
- `FakeRuntimeAdapter` 保留现有浏览器上传快照流程，或显式返回不支持 runtime capture。
- `DockerSwarmAdapter` 使用与本地相同的业务端口，但底层实现必须结合服务器 Volume 方案。
- Django Web 不挂载 Docker Socket；只有 runtime-worker 和 storage-worker 可以调用 Docker API。

### 5.6 Storage Worker

Compose 新增 `workspace-storage-worker`：

- 使用独立 Celery 队列 `q_workspace_storage`。
- 只接收 `storage_job_id` 和 trace_id。
- 与 runtime-worker 分离并设置最小并发。
- 需要 Docker API 的环境才挂载 Docker Socket。
- 不开放端口，不接受浏览器请求。
- 使用和业务 service 相同的 CAS、审计、Outbox、失败与补偿机制。

CAPTURE 顺序：

```text
锁定并校验 StorageJob
  -> 状态改为 RUNNING
  -> 校验 Session、任务、实例、capability 和版本
  -> adapter.capture_workspace(main.py)
  -> 大小、UTF-8、路径和 ClamAV 校验
  -> MinIO put_stream
  -> register ObjectAsset + CLEAN scan fact
  -> 创建 WorkspaceSnapshot 和 AutosaveLog
  -> CAS 更新 WorkspaceSession.current_version/latest_snapshot
  -> StorageJob PASSED
  -> Audit + Outbox + SSE invalidation
```

外部 I/O 不能包在长数据库事务中。应先声明作业、执行 I/O，再用短事务提交结果；中间失败产生可重试 FailureRecord，已上传但未落库的对象进入孤儿清理。

RESTORE 顺序：

```text
锁定并校验 StorageJob
  -> 校验快照 asset/digest/scan/status
  -> 下载 MinIO 对象
  -> adapter.restore_workspace(main.py)
  -> 回读并确认 digest
  -> 创建新的 WorkspaceSnapshot 版本事实
  -> 更新 Session
  -> StorageJob PASSED
  -> Audit + Outbox
```

### 5.7 API 契约

建议新增：

```text
POST /api/v2/tasks/{task_id}/workspace-storage-jobs
GET  /api/v2/workspace-storage-jobs/{job_id}
```

CAPTURE 请求：

```json
{
  "kind": "CAPTURE",
  "client_seq": 12,
  "base_version": 4
}
```

RESTORE 请求：

```json
{
  "kind": "RESTORE",
  "snapshot_id": "<workspace-snapshot-id>"
}
```

POST 必须携带：

- Portal Session 和 workspace HttpOnly Cookie。
- `Idempotency-Key`。
- `If-Match`，目标为当前 WorkspaceSession row_version。

成功创建返回 `202 Accepted`、作业 DTO、`Location` 和当前 ETag。查询接口只允许当前学生读取当前任务作业。

建议稳定错误码：

- `WORKSPACE_STORAGE_JOB_ACTIVE`
- `WORKSPACE_CAPTURE_UNSUPPORTED`
- `WORKSPACE_FILE_MISSING`
- `WORKSPACE_FILE_TOO_LARGE`
- `WORKSPACE_FILE_INVALID`
- `WORKSPACE_CAPTURE_CONFLICT`
- `WORKSPACE_CAPTURE_FAILED`
- `WORKSPACE_RESTORE_FAILED`
- `WORKSPACE_SNAPSHOT_NOT_READY`
- `WORKSPACE_VOLUME_UNAVAILABLE`

现有 multipart `PUT /tasks/{id}/workspace-snapshot` 暂时保留给 FakeRuntime。真实 Runtime 页面不得再把 textarea 内容发送到该接口。

### 5.8 Workbench 只读契约

`GET /api/v2/tasks/{task_id}/workbench` 增加经过裁剪的字段：

```json
{
  "workspace": {
    "mode": "RUNTIME_IDE",
    "entrypoint": "main.py",
    "capture_supported": true,
    "last_synchronized_version": 4,
    "active_storage_job": null
  }
}
```

不得返回 adapter 内部 endpoint、容器 ID、Volume 名称、上游 token 或对象存储 key。

模式建议：

- `LEGACY_DRAFT`：FakeRuntime，保留 textarea 上传。
- `RUNTIME_IDE`：真实 Runtime，只使用 iframe 和服务端捕获。
- `READ_ONLY`：任务终态或工作区不可用。

### 5.9 前端交互

用户端工作台按 `workspace.mode` 渲染：

- `LEGACY_DRAFT` 保留现有 textarea 与离线队列，服务既有 FakeRuntime 回归。
- `RUNTIME_IDE` 隐藏外层 textarea，以 WebIDE iframe 为唯一编辑入口。
- 保存按钮改为“同步并保存”，创建 CAPTURE 作业。
- 作业执行期间禁用重复保存、运行测试、检查点和提交。
- 通过 SSE 失效 workbench/storage job Query；断线时轮询作业状态。
- 成功后显示“已同步 vN”，失败显示稳定错误和 trace_id。
- 运行测试前必须存在最近一次成功 CAPTURE；测试明确绑定该 snapshot_id。
- 检查点恢复显示异步 RESTORE 进度，成功后要求 WebIDE 刷新文件内容。

第一版不尝试从 code-server 获取精确 dirty 状态。页面使用：

- `尚未同步`
- `正在同步`
- `已同步 vN`
- `同步失败`
- `版本冲突`

不得在没有编辑器协议的情况下显示“已保存”。后续若需要实时 dirty 状态，应通过受控 code-server 扩展和 `postMessage` 协议单独实现，并校验 origin、session 和消息 schema。

教师端模板页面必须允许逐项选择 capability，默认只启用已经由所选镜像和预检证明可用的能力，禁止继续固定声明全部能力。

## 六、安全要求

### 6.1 容器安全

- 非 root。
- `read_only` 根文件系统。
- `cap_drop=ALL`。
- `no-new-privileges`。
- 明确 CPU、内存、PID、磁盘和 TTL。
- 不挂载宿主机目录、Docker Socket 或平台 Secret。
- 不发布宿主机端口。
- 默认不允许外网；依赖下载必须走受控镜像构建或审批后的策略。

### 6.2 网络隔离

- 工作区路由必须验证实例级 token。
- 一个任务 token 不得访问其他任务。
- workspace-gateway 继续校验 Portal Session、workspace token、capability、任务状态和实例状态。
- teacher/admin Host 对 `/workspace/` 继续返回 403。
- WebSocket 必须执行与 HTTP 相同的上游 token 注入与校验。
- 内部授权失败不得回退为直接访问 runtime endpoint。

### 6.3 文件安全

第一版只允许相对路径 `main.py`：

- 拒绝绝对路径、空路径、`..` 和路径分隔符变体。
- 限制单文件最大尺寸。
- 只接受普通文件和 UTF-8 文本。
- 拒绝软链接、硬链接、设备文件和 FIFO。
- 捕获和恢复均验证 digest。
- MinIO 上传后必须登记 owner、purpose、版本和保留期。

### 6.4 敏感信息

下列内容不得进入浏览器 JSON、URL、localStorage、日志、SSE、Outbox 或证据包：

- workspace token、实例级上游 token、Session Cookie。
- Docker Socket、容器环境变量、Registry 密码。
- MinIO secret、内部 object key、预签名 URL。
- hidden tests、期望输出和 judge 内部路径。
- 完整学生源码；日志只记录 digest、大小、状态和引用 ID。

## 七、本地验证到服务器部署

### 7.1 本地阶段 真实工作区-L

本地阶段必须使用 Compose 和 `DOCKER_LOCAL`：

1. 构建真实工作区镜像。
2. 启动内部 Registry，或推送到本地可访问的私有 Registry。
3. 使用 `repository@sha256:digest` 拉取并验证，不只使用可漂移 tag。
4. 注册 CLEAN/APPROVED ImageAsset。
5. 创建真实 `DOCKER_LOCAL` Runtime Adapter、资源规格和模板版本。
6. 发布新的实验并生成新的个人任务。
7. 完成 WebIDE、CAPTURE、RUN_CHECK、RESTORE、提交和回收旅程。
8. 记录镜像 manifest digest、容器 image ID、迁移 head、OpenAPI revision 和证据目录。

`LOCAL_RUNTIME_IMAGE` 可以作为本地 Engine 的解析覆盖，但其值必须固定为本次验证的明确版本或 digest，并与任务冻结镜像建立可审计映射。不得以 `:latest`、未记录的 `:local` 或 Compose 构建缓存作为出口证据。

### 7.2 服务器阶段 真实工作区-S

服务器阶段使用同一镜像 digest 和 `DOCKER_SWARM`：

- 私有 Registry、节点拉取认证和 digest 校验。
- runtime 节点标签与 placement constraint。
- 加密 overlay 网络和任务 DNS。
- workspace-gateway 到任务服务的 HTTP/WebSocket 可达性。
- 实例级上游 token 在 Swarm Secret/受控配置中的注入方式。
- 工作区 Volume 的跨节点持久化或快照恢复策略。
- 节点故障、任务重调度、Session 失效和最近快照恢复。
- 三 Manager quorum、容量、性能、回滚和孤儿资源回收。

服务器 Volume 必须二选一并记录 RPO/RTO：

1. 使用经过验收的分布式/外部 Volume 驱动；或
2. 使用节点本地临时 Volume，并在重建时从 MinIO 最近快照恢复，明确接受最后一次同步之后的未同步内容可能丢失。

本地通过只能标记“本地通过（真实环境待验收）”，不能写成服务器或生产就绪。

## 十、Docker 验证门禁

所有命令由仓库脚本编排 Docker 容器执行。宿主机只负责调用 Docker CLI，不直接运行 Python、Node、pytest、mypy、npm 或 Playwright。

需要新增统一入口，例如：

```text
scripts/verify-真实工作区-docker.ps1
scripts/verify-真实工作区-integration.ps1
scripts/真实工作区-promote-image.ps1
scripts/真实工作区-server-smoke.ps1
```

静态和单元门禁必须使用专用 test image：

- backend test image 使用 `requirements/dev.txt`。
- frontend test image 使用锁定的 Node 基础镜像和 `npm ci`。
- OpenAPI 生成和类型比较在容器中完成。
- 不挂载宿主机 `.venv` 或 `node_modules`。

本地集成至少覆盖：

- 镜像以非 root、只读 rootfs 启动。
- `/healthz`、WebIDE 静态资源和 WebSocket。
- 正确/错误上游 token。
- 跨任务、跨学生、跨 Portal 拒绝。

- RUN_CHECK 使用指定 snapshot，不读取实时 Volume。
- Session 过期、容器消失、Volume 消失和 Docker Engine 中断。
- 最终同步与容器/Volume/孤儿对象清理。
- 1440px、920px、390px 工作台无溢出，iframe 与底栏不遮挡。

- 网关跨节点访问工作区服务。

- Registry、MinIO、Redis 短时故障和恢复。
- 并发创建、同步、测试和销毁的容量边界。

## 十二、回滚策略

代码回滚：

- 保留 `LEGACY_DRAFT` 和 FakeRuntime 路径，真实工作区通过 feature/config gate 开启。
- 数据库 migration 只增加表、字段、约束和索引，不删除旧快照字段或接口。
- 回滚前停止创建新的 StorageJob，等待运行作业终态或显式取消。

镜像回滚：

- 使用上一个已验证 digest 创建新任务实例。
- 已运行实例不热替换镜像；撤销 Session 后按最近快照重建。
- 不修改历史任务冻结事实。

数据回滚：

- 已写入 MinIO 的不可变快照不删除。
- 未关联对象由对账任务按 retention 清理。
- Volume 删除必须晚于最终快照确认；删除失败进入补偿队列。

## 十三、完成标准

真实工作区-L 本地完成必须同时满足：

- 真实 WebIDE 替代占位页。
- 工作区容器只包含环境，用户文件只写入任务 Volume。
- Storage Worker 能初始化、捕获和恢复 `main.py`。
- 测试、检查点、提交和归档引用正确的不可变快照。
- FakeRuntime 和历史任务无回归。
- 实例级上游鉴权阻断跨任务访问。
- 全部有效证据来自 Docker 集成环境。
- 镜像、migration、OpenAPI、配置和测试证据完整记录。
- 出口结论只能是“本地通过（真实环境待验收）”或“未通过”。

真实工作区-S 服务器完成还必须满足：

- 服务器运行与本地验证完全相同的镜像 digest。
- Swarm、Registry、Secret、overlay 网络和 Volume 方案通过真实环境验收。
- 节点故障恢复、容量、性能、回滚、RPO/RTO 有可复核证据。
- 无未标记的安全、数据一致性或运维阻塞项。

## 十四、明确禁止

- 禁止用另一个容器的可写层充当持久存储。
- 禁止 `docker commit` 保存学生工作区。
- 禁止把 Docker Socket 挂载给 Django Web、workspace-gateway 或学生工作区。
- 禁止工作区直接访问 MinIO、MySQL、Redis 或平台内部授权接口。
- 禁止浏览器提交容器 ID、Volume 名称、内部 endpoint 或对象 key。
- 禁止真实 Runtime 继续使用前端 textarea 作为测试源码事实。
- 禁止检查点只改数据库而不恢复在线文件。
- 禁止 capability 声明与镜像实际能力不一致。
- 禁止本地验证后在服务器重新构建镜像。
- 禁止用宿主机 Python、Node 或依赖测试结果作为阶段出口证据。
