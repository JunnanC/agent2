# Bug-3 源码诱因分析报告

日期：2026-11-09（北京时间）
项目：JunnanC/agent2
分析基线：`d231289085e2889183cb4e269a0289388a8013a3`（当前 `origin/main`）
依据：[三门户浏览器续验报告](agent2-三门户浏览器续验报告.md)。线上现象引用原报告，本次尚未复测生产。

## 一、结论摘要

1. 学生任务评审提示是已定位的前端状态判断错误。`IN_PROGRESS` 被纳入 `hasReview`，评审接口 404 又被当作空结果，空结果固定显示“教师正在评审”。这与真实任务状态无关。
2. HTTPS 域名登录失败是已确认的部署配置缺口。生产 Django 从 `DJANGO_TRUSTED_ORIGINS` 读取 CSRF 可信来源；原报告的独立校验确认三个 HTTPS 域名不在生效列表。当前代码没有把部署使用的域名与可信来源做一致性检查。
3. `RUNTIME_ENGINE_UNAVAILABLE` 的源码根因是管理概览在 `django` 容器直接读取 Docker 运行时，而 Docker socket 按安全契约只挂载给 `runtime-worker`。逐适配器的其他故障仍需线上日志确认。

## 二、证据与调用链

### 学生评审提示

`frontend/apps/student-web/src/pages/task-detail.tsx` 将 `IN_PROGRESS`、`REPORT_DRAFT` 等状态算入 `hasReview`；启用 `reportApi.reviewResult()` 后，把 404 错误置空，`reviewedRound` 为空时统一显示“教师正在评审”。原报告的任务状态为 `IN_PROGRESS`，教师端显示未提交，评审接口 404，因此页面文案没有事实依据。已有组件测试检查完成评审和退回草稿，未覆盖“进行中且无评审”。

### HTTPS 登录

`backend/education_experiment_platform/settings/prod.py` 直接使用 `DJANGO_TRUSTED_ORIGINS`；`scripts/cd/deploy.sh` 从服务器私有 `.env` 拷贝配置，预检未比对 `STUDENT_HOST`、`TEACHER_HOST`、`ADMIN_HOST` 的 HTTPS 来源。原报告确认线上生效设置缺少这些来源，并且正确 CSRF token 下 HTTPS 请求仍被拒绝。这是配置与部署校验问题，不是前端重试逻辑可以解决的错误。

### 运行时告警

`backend/apps/analytics/observability.py` 的 `operations_summary()` 在 `django` 请求进程直接调用 `runtime_inventory_snapshot()`。后者逐个调用已启用 Docker 适配器的 `health()`，一个不可用就汇总为 `UNAVAILABLE` 并触发 P1 告警。`docker-compose.dev.yml` 把 Docker socket 和组权限只授予 `runtime-worker`，且基础设施契约测试明确禁止把 socket 授予 `django`。因此管理概览当前执行位置与所需权限不匹配。原报告没有逐适配器数据，不能排除生产同时存在其他引擎故障。

## 三、范围与验证边界

学生问题可用组件回归测试验证。CSRF 需在部署前校验配置，最终仍需用真实 HTTPS 域名登录验证。运行时需先读取生产 `runtime.drivers`、服务日志和 Docker 访问状态，再决定具体修复；在缺少证据前只做诊断，不改引擎健康语义。原报告未验证工作区实际执行，故不推断执行是否受影响。
