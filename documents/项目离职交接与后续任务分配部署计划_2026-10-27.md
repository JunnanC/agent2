## 六、部署与发布顺序

当前任务是制定部署安排，不代表已获真实服务器、Registry 凭据或生产发布授权。建议分为三道环境门：

### 1. 本地集成门

- 使用 `docker-compose.dev.yml`，为每次全链路验证设置唯一 Compose project 名；测试环境数据与开发者日常数据隔离。
- 先运行受影响模块定向测试，再执行后端 `manage.py check`、迁移漂移检查、pytest、Ruff、mypy、OpenAPI validate；前端执行各 app 的 typecheck、lint、Vitest 和 build。
- 运行 P15/P16 要求的端到端用户旅程与关键异常：环境失败重试、SSE 断开回退、Session 过期、离线保存恢复、If-Match 冲突（412）、重复请求幂等、任务撤回/过期后只读。
- 使用 `scripts/verify-p16-integration.ps1` 前先阅读参数和清理行为，分配唯一项目名/端口/证据目录；确认脚本结束后容器、网络、卷等资源按预期清理。证据脱敏，不保留 Cookie、Token、签名下载 URL。
- 通过后只能记录“本地通过（真实环境待验收）”。不得把单机 Docker/Compose 结果描述成 HA 或生产就绪。

### 2. 真实预发布门

- A 确认部署窗口及业务负责人；D 维护环境检查表并执行获批部署；C 确认 migration、健康检查、worker/运行时和 API revision，B 验证三端构建与静态资源；A 仅在明确范围内协助后端。
- 在部署前冻结 Git commit SHA、OpenAPI revision、数据库 migration 列表、所有 OCI 镜像 digest 和回滚版本。真实服务器按指定 digest 拉取，不能在服务器临时重新 build 后直接上线。
- 检查 Swarm 三 Manager quorum、节点角色标签、入口/DNS/TLS、私有 Registry 鉴权、可信代理网段、防火墙、外部 MySQL/Redis/MongoDB/MinIO 的持久化与备份恢复、Swarm Secrets/Configs、监控和日志。
- Secrets 只能通过批准的 Secrets 管理流程传递；不放入 Git、配置明文、镜像、命令历史、截图或测试报告。

### 3. 正式发布与回滚门
