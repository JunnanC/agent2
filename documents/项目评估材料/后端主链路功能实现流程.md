# 教学云实验平台后端主链路功能实现流程

源码导读与功能实现说明

本文按请求进入系统后的实际处理顺序，说明教师模板配置、实验发布、学生环境准备、快照与检查点、用例测试和教师评阅。重点解释接口层、业务服务、数据库、异步任务与运行时之间如何协作。内容依据当前代码结构整理，流程边界和运行驱动仍需在项目环境中联调验收。

## 主链路总览

![实验主链路](D:/all_of_project/edu-agent-platform/documents/项目评估材料/配图/实验主链路.png)

这条链路不是一个接口一次做完，而是多个有状态的请求与后台任务协作完成：

1. 教师建立模板及版本，配置章节、任务、运行镜像和自动检查规则。
2. 模板版本通过预检并发布后，教师基于该版本创建实验发布草稿。
3. 发布实验后，后端冻结发布快照并给目标选课记录生成学生任务。
4. 学生启动任务后，后端创建 provisioning job，后台 worker 按阶段准备容器。
5. 实例就绪后学生进入工作区；代码快照进入对象存储，检查点引用快照。
6. 测试请求绑定具体快照并异步执行；学生提交报告后，教师评分、批注并作出决定。

## 一 教师创建与发布实验模板

### 1. 创建模板和草稿版本

**前端入口**：`frontend/apps/teacher-web/src/pages/templates.tsx` 的 `create` mutation 调用 `teachingApi.createTemplate`。编辑器在 `template-editor.tsx` 建立版本并维护章节、任务、环境及执行规格。

**请求入口**：`apps/labtemplates/views.py` 的 `TemplateListView.post` 接收请求，DRF `TemplateWriteSerializer` 校验名称等字段。接口使用教学端权限，并通过幂等请求封装避免客户端重试重复创建。

**业务处理**：`apps/labtemplates/services.py::create_template` 检查教师是否具有课程模板管理权限，清理名称后在 MySQL 创建模板，记录审计信息并发出模板创建事件。随后 `create_version` 基于模板建立可编辑的版本记录。

### 2. 写入章节、任务和执行环境

章节和实验任务分别由章节、任务集合接口写入。编辑器保存后会重新读取版本，更新 `row_version` / ETag；后续修改携带 `If-Match`，服务端发现版本已变化就拒绝过期写入，避免并发编辑覆盖。

版本中的运行配置包括 runtime adapter、镜像、资源配置、工作区能力和报告/评阅策略。执行规格还定义语言、入口文件、超时、内存、CPU、比较方式、测试数据资源及网络模式。当前表单与后端校验限定的执行边界以 Python 单文件和 `DENY_ALL` 网络为主，不应介绍为任意语言的通用在线判题平台。

`save_execution_spec` 校验规格及测试 JSON，注册测试资源并更新草稿版本；`jsonschema` 用于检查自动检查规则的 JSON Schema 结构。它们用途不同：前者校验执行配置和测试数据，后者校验规则定义。

### 3. 预检并发布模板版本

编辑器先调用版本预检，后端检查模板版本配置、资源和运行前置条件，创建可追踪的预检记录；耗时步骤由异步任务执行并写回阶段结果。预检通过后，`PublishVersionView` 将请求交给模板版本发布逻辑，将草稿内容固定为可供实验发布引用的版本。

这里有两个容易混淆的“发布”：

- **发布模板版本**：冻结模板定义，使实验发布可以引用确定的版本。
- **发布实验给学生**：根据课程、选课对象和时间设置创建学生任务，是下一节的业务动作。

相关代码：`apps/labtemplates/views.py` 的 `TemplateListView`、`ExecutionSpecSaveView`、`PublishVersionView`；`apps/labtemplates/services.py` 的 `create_template`、`create_version`、`save_execution_spec`；前端 `template-editor.tsx`。

## 二 按模板创建并发布实验

教师在实验发布页选已发布的模板版本、评分量规、目标选课人群、开放时间、截止时间及报告策略，先创建 `DRAFT` 发布记录，再单独执行“发布”动作。

发布动作进入 `apps/experiments/views.py::TeachingPublicationActionView`，子类 `PublishPublicationView` 将请求交给 `publish_publication`。业务服务按以下顺序处理：

1. 使用 `select_for_update` 锁定课程和发布记录；检查教师的发布权限、草稿状态及 `If-Match` 版本。
2. 检查模板版本、镜像、资源配置等发布依赖，生成模板内容快照和运行时快照。
3. 固定目标选课记录集合，并计算内容摘要和发布摘要，避免发布后模板变化影响已发布任务。
4. 目标人数少于配置阈值时，在当前事务中生成每个学生的 `ExperimentTask`；达到阈值时先标记 `PUBLISHING`，事务提交后由 Celery 分批生成。
5. 写入审计及发布事件。若启用自动预热，提交后另行触发镜像预热任务。

`transaction.on_commit` 的作用是仅在数据库成功提交后才发队列任务，避免 worker 抢先运行却读不到未提交记录。批量任务分发的异步分支以配置阈值为条件，不意味着每次发布都走异步流程。

相关代码：`apps/experiments/services.py::publish_publication`、`execute_publication_assignment_chunk`；`apps/experiments/views.py::PublishPublicationView`；前端 `frontend/apps/teacher-web/src/pages/publishing.tsx`。

## 三 学生启动任务与准备实验环境

学生点击开始实验后，`apps/experiments/views.py::UserTaskStartView` 调用 `start_task_runtime`，继而调用 `apps/provisioning/services.py::start_provisioning`。服务端先检查任务所属学生、发布状态、选课有效性、实验开放时间、前置任务及资源配置，拒绝浏览器传入的运行参数覆盖，再创建或复用 provisioning job 和资源配额预留。

任务状态从 `ASSIGNED` 进入 `PROVISIONING`，后台 worker 执行 `execute_provisioning_job`，按阶段记录进度：

| 阶段 | 处理内容 |
| --- | --- |
| `QUOTA_CHECK` | runtime adapter 检查资源配额和可用容量。 |
| `IMAGE_PREPARE` | 确认镜像已批准且扫描通过，准备运行镜像。 |
| `CREATE` | 调用 Docker/Swarm adapter 创建学生运行实例，持久化外部实例引用。 |
| `NETWORK_ATTACH` | 按所选运行适配器配置工作区网络。 |
| `BOOT_PROBE` | 检查实例状态，确认运行环境可用。 |
| `WORKSPACE_READY` | 写入 endpoint 与就绪时间，实例标记为 `READY`。 |

全部阶段通过后，任务转换到 `READY`，服务为学生签发工作区 session 和短期 token。学生进入工作台时，`UserTaskEnterView` 再检查发布窗口、任务状态和实例必须为 `READY`，然后转换任务状态并签发/轮换 session。也就是说，点击开始会启动环境准备；不能把前端打开工作台本身理解成容器同步创建成功。

运行适配器由 `runtime_for_driver` 按 driver/config 选择。仓库同时有 `FAKE`、本地 Docker 和 Swarm 实现；`FAKE` 用于模拟/测试，不能当作真实容器执行证据。是否实际连接 Docker Engine 或 Swarm，需要核对当前环境的 driver、`LOCAL_RUNTIME_MODE`、runtime 配置与 Docker Context。

相关代码：`apps/experiments/views.py::UserTaskStartView`；`apps/experiments/services.py::start_task_runtime`；`apps/provisioning/services.py::start_provisioning`、`execute_provisioning_job`；`apps/provisioning/tasks.py::run_provisioning_job`；`apps/provisioning/adapters.py::runtime_for_driver`、`DockerLocalAdapter`、`DockerSwarmAdapter`。

## 四 保存代码快照与检查点

### 代码快照保存

工作区前端持有 session token，并随代码内容、`client_seq` 与 `base_version` 调用快照接口。`UserWorkspaceSnapshotView.put` 校验上传内容及版本参数，然后进入 `save_snapshot`：

1. 根据任务、学生及活动 session 验证归属和 `snapshot` 能力。
2. 读取上传文件并计算摘要；相同序号、相同摘要的重试可返回既有结果，序号冲突或基准版本过期则拒绝。
3. 通过 ClamAV 扫描文件；扫描服务不可用或文件不干净时不将快照标记为正常。
4. 使用 boto3 S3 接口将对象写入 MinIO，并在 MySQL 注册 ObjectAsset 与 WorkspaceSnapshot 元数据。
5. 通过记录版本比较并交换更新 session 当前版本，保存 autosave 日志、审计记录和事件。

MinIO 保存文件内容，MySQL 保存对象引用、摘要、版本和归属。对象写入与数据库事务并非一个跨服务原子事务；异常清理和后续一致性检查用于处理部分失败。

### 检查点创建

学生点“保存检查点”后，`UserCheckpointListCreateView.post` 调用 `create_checkpoint`。服务端再次检查学生任务归属、有效 session、token 和 `checkpoint` 能力；要求当前 session 已有最新快照。随后新建检查点记录，保存序号、快照引用、快照摘要、来源 client sequence 和保留期限，并写审计与事件。

因此，检查点是一个“命名的快照引用”，不是复制整台容器，也不是 Docker 镜像或系统内存快照。恢复检查点时，后端依据引用恢复快照；大对象恢复可能创建异步 storage job，接口返回 `202`，需要继续查询 job 状态。

相关代码：`apps/workspaces/views.py::UserWorkspaceSnapshotView`、`UserCheckpointListCreateView`、`UserCheckpointRestoreView`；`apps/workspaces/services.py::save_snapshot`、`create_checkpoint`、`restore_checkpoint`；`apps/core/object_storage.py::S3ObjectStorage`；`apps/core/antivirus.py::ClamAVScanner`。

## 五 执行用例测试

学生在工作台触发测试，前端 `frontend/apps/student-web/src/pages/workbench.tsx` 调用 `workspaceApi.createExecutionRun`。后端 `UserExecutionRunListView.post` 检查任务、活动 session 和 token，再进入 `request_execution_run`：

1. 锁定 session，确认会话归属于当前学生；选择本次测试所用的快照。
2. 按 session、快照和 request key 生成幂等键；重复请求返回既有 execution run，避免误建多条记录。
3. 从已发布任务快照读取执行规格，并生成执行命令摘要、资源限制和规则摘要。
4. 写入 `QUEUED` 执行记录；真实运行驱动在数据库事务提交后通过 Celery 调度 worker。
5. worker 将记录改为 `RUNNING`，读取 MinIO 中固定版本的学生代码和测试数据，调用 adapter 执行。
6. adapter 按超时、CPU、内存和网络限制创建一次性 judge 容器；当前 Docker 本地执行路径要求命令格式符合允许列表、网络模式为 `DENY_ALL`，并挂载只读测试文件。
7. worker 收集 stdout、stderr、测试报告及状态；输出文件写入 MinIO，执行记录更新为 `PASSED`、`FAILED`、`TIMEOUT` 等状态，前端重新查询记录。

**重要边界**：当任务 driver 为 `FAKE` 时，当前实现可直接返回模拟通过结果，不会因此证明用户代码在真实 Docker 中执行成功。汇报实际运行结果前应核对任务使用的 driver 和运行配置；测试链路仍需真实环境端到端验收。

相关代码：`apps/workspaces/views.py::UserExecutionRunListView`；`apps/workspaces/services.py::request_execution_run`、`execute_execution_run`；`apps/workspaces/tasks.py::execute_workspace_execution_run`；`apps/provisioning/adapters.py::DockerLocalAdapter._run_container`；前端 `workbench.tsx`。

## 六 报告提交与教师评阅

学生提交报告后形成报告版本并进入待评阅流程；若模板定义了自动检查规则，后端创建 auto-check run，并在事务提交后通过 Celery 调度。检查结果写回自动检查记录，评阅决策接口会阻止仍有 `QUEUED` 或 `RUNNING` 的检查任务时提前定案。

教师打开评阅页面后，可以保存量规评分、报告批注，最后选择通过或退回。`TeachingReviewDecideView.post` 校验请求并读取 `If-Match` 记录版本，再调用 `decide_review`：

1. 确认教师门户上下文、课程评阅权限，并锁定课程、实验任务和评阅记录。
2. 检查评阅版本未过期、记录尚未定案，实验任务确实处于 `UNDER_REVIEW`。
3. 确认没有尚未完成的自动检查，且每个启用的评分标准都已有评分。
4. 后端根据各标准分数重新计算总分；若请求携带的总分不一致就拒绝，不以浏览器传来的总分为准。
5. 保存决定及评分快照，更新 Review 状态，并转换 ExperimentTask 状态。
6. 通过时请求任务正常结束；退回时重开报告草稿或恢复实验进行状态，供学生修改后再次提交。

前端 `frontend/apps/teacher-web/src/pages/reviews.tsx` 保存分数和决定时携带当前 row version；成功后刷新评阅列表。后端数据库状态才是最终事实，SSE 或前端提示只是通知/刷新机制。

相关代码：`apps/reviews/views.py::TeachingReviewDecideView`；`apps/reviews/services.py::decide_review`、`_enqueue_auto_check_runs`；`apps/reviews/tasks.py::run_auto_check`；`frontend/apps/teacher-web/src/pages/reviews.tsx`。

## 七 常用一致性与排错思路

| 现象 | 优先检查 |
| --- | --- |
| 发布后学生没有任务 | 检查模板/镜像/量规、选课状态、发布时间、发布权限及 row version；再查批量 assignment worker 是否消费。 |
| 任务或工作区不可用 | 查看 provisioning 阶段和失败码、镜像批准/扫描、adapter 与 worker 健康；确认实例为 `READY`，endpoint/gateway 可达，session、cookie、token、Origin 和工作区能力匹配。 |
| 快照冲突或测试无结果 | 比对 client sequence、base version 和 session 版本；检查 ClamAV/MinIO、执行快照/测试资源、worker 队列和任务 driver，确认是否误用 `FAKE`。 |
| 评阅无法定案 | 检查教师权限、评阅与任务状态、If-Match 版本、自动检查是否完成、量规是否全部打分及总分是否匹配后端计算。 |

异步链路按“请求记录任务 → 事务提交 → 队列投递 → worker 执行 → 更新任务状态 → 前端轮询/事件刷新”的顺序排查。看到 HTTP 请求成功或 Celery 已入队，不代表容器已经就绪或业务已完整完成。
