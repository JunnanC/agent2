# 本地算法运行时改造任务拆分

## 一、目标与边界

本任务用于把当前工作区的 `FakeRuntime` 操作验证，扩展为可以在本地 Docker 环境执行真实算法的完整流程：

```text
任务发布
  -> 学生任务冻结执行规则
  -> 创建学生专属工作区容器
  -> 编辑并保存代码快照
  -> 创建一次性 judge 容器
  -> 编译/执行算法
  -> 保存测试结果与执行证据
  -> 提交报告
  -> 教师自动检查与审核
  -> 任务完成与资源回收
```

本地 Docker 结果只允许记录为“本地通过（真实环境待验收）”。服务器部署仍按 P14 的 Docker Swarm、HA、恢复和性能门禁执行。

P07 的 FakeRuntime 不删除、不改变既有测试语义；真实本地运行时作为 P14 的本地扩展接入。当前已有的 FakeRuntime 任务不直接改造，真实算法验证使用新的种子任务。

## 二、严格顺序

每个任务完成后，必须填写 [`本地算法运行时_阶段出口记录模板.md`](./执行记录/本地算法运行时_阶段出口记录模板.md)，并达到“本地通过（真实环境待验收）”后才能开始下一任务。

| T02 | P05 | 算法执行规范 | 模板 `execution_spec`、测试资产、命令白名单 |

## 三、任务定义

### T00：P00-P03 基线确认

不修改业务代码。确认 P00-P03 已达到本地门禁，并记录：

- 当前 Compose 配置版本和镜像版本；
- 当前 migration head 与 OpenAPI revision；
- 当前 P07/P08 FakeRuntime 任务、学生和教师 ID；
- `manage.py check`、后端测试、前端构建和入口 smoke 结果；
- 工作树中不属于本任务的已有修改。

下一任务输入：基线记录、migration head、OpenAPI revision、Compose 版本。

### T01：P04 本地运行时治理扩展

修改治理目录，使本地 Docker 与 FakeRuntime 可以被明确区分：

- `RuntimeAdapter.Driver` 增加 `DOCKER_LOCAL`；
- 增加本地 Docker adapter 的 `config_ref`；
- 复用 `ResourceProfile` 的 CPU、内存、磁盘和网络限制；
- 增加本地运行时配置项：`LOCAL_RUNTIME_IMAGE`、`LOCAL_RUNTIME_NETWORK`、`LOCAL_DOCKER_HOST`；
- Django Web 不挂载 Docker Socket，只有 runtime-worker 可以访问 Docker Engine。

验收重点：driver 约束、配置校验、配额边界、网络策略和权限隔离。

下一任务输入：`runtime_adapter_id`、`config_ref`、`resource_profile_id`、网络策略和本地环境变量清单。

### T02：P05 算法模板执行规范

为 `TemplateVersion` 增加执行配置，第一版只支持 Python 单文件算法：

```json
{
  "language": "python",
  "entrypoint": "main.py",
  "timeout_seconds": 5,
  "memory_mb": 256,
  "cpu_millicores": 500,
  "comparator": "token",
  "tests_asset": "<asset-public-id>",
  "network_mode": "DENY_ALL"
}
```

执行配置必须进入模板预检、`spec_digest`、发布快照和 OpenAPI。学生不能提交任意 shell 命令，服务端只根据语言和模板生成允许的执行命令。

验收重点：正确配置通过预检，超时、网络放宽、非法命令和未扫描测试资产被拒绝。

下一任务输入：`template_version_id`、`template_spec_digest`、`execution_spec`、测试资产 ID。

### T03：P06 发布与个人任务冻结

确认发布任务时冻结模板版本和执行规则：

- 任务引用已发布的 `TemplateVersion`；
- 任务使用固定的 `spec_digest`；
- 任务使用固定的 runtime adapter、镜像和资源配置；
- 新建独立的本地算法实验种子任务；
- 不修改现有 FakeRuntime 任务的数据事实。

验收重点：模板后续修改不能影响已分配任务，跨学生任务不能读取对方的执行配置。

下一任务输入：`algorithm_task_id`、`student_id`、`teacher_id`、任务模板 digest。

### T04：P07 装载兼容

P07 仍以 FakeRuntime 为默认测试驱动，只做兼容工作：

- 保持 `RuntimeAdapter` 协议不变；
- 增加 `DOCKER_LOCAL` 所需的协议测试桩；
- 保持六阶段装载、重试、部分成功和补偿语义；
- 确认 FakeRuntime 的现有测试、种子和出口记录不回归。

本阶段不创建真实 Docker 容器。

下一任务输入：`RuntimeSpec`、`ProvisioningJob`、`ProvisioningInstance` 及其阶段事件契约。

### T05：P08 工作区执行生命周期

新增真实执行记录，例如 `WorkspaceExecutionRun`，至少包含：

- task、session、snapshot；
- `QUEUED/RUNNING/PASSED/FAILED/TIMEOUT/RESOURCE_EXCEEDED/REJECTED`；
- 执行规则摘要和 digest；
- 标准输出、错误输出、测试报告资产引用；
- 开始时间、结束时间、耗时、trace_id。

修改 `RUN_CHECK`：

- FakeRuntime 下保持兼容结果；
- 真实 adapter 下创建执行记录并异步执行；
- 返回执行 ID；
- 增加执行结果查询接口；
- 前端显示执行中、通过、失败、超时和资源超限状态。

验收重点：幂等、重复请求、过期 session、跨任务访问、状态冲突和结果审计。

下一任务输入：`execution_run_id`、`snapshot_id`、`task_id`、`session_id`。

### T06：P09 报告与执行证据

报告提交时关联最新有效执行结果：

- 报告中保存执行结果摘要；
- 标准输出、错误输出和测试报告作为不可变对象资产；
- 报告提交后执行证据不能被学生修改；
- 教师读取报告时能看到执行证据和对应快照。

验收重点：正确算法、错误算法、无执行结果、过期执行结果和跨任务资产访问。

下一任务输入：`report_submission_id`、`execution_run_id`、结果资产 ID。

### T07：P10 教师自动检查

保留 `FakeRuntimeAutoCheckExecutor`，新增真实执行器接口：

- 学生运行和教师自动检查共用执行规则；
- 教师检查使用独立 judge 容器；
- 自动检查结果写入审核事实；
- 教师仍可手动补充评语或覆盖自动检查结论；
- 学生不能修改测试命令和隐藏测试资产。

验收重点：通过、失败、超时、自动检查重试和教师手动审核。

下一任务输入：`review_id`、`auto_check_run_id`、模板执行规则和执行结果。

### T08：P11 容器与证据回收

把运行时资源接入现有归档和补偿机制：

- 任务过期、取消、完成时撤销工作区票据；
- 销毁学生工作区容器；
- 销毁一次性 judge 容器；
- 按 retention 清理临时卷和执行对象；
- 对账发现孤儿容器、孤儿卷和数据库实例；
- 删除失败时创建补偿任务，不直接修改业务终态。

验收重点：幂等删除、部分删除成功、Docker Engine 不可用、重试和资源最终一致性。

下一任务输入：managed labels、external_id、TTL、retention 和补偿任务类型。

### T09：P13 观测与运维

增加以下观测事实：

- 容器创建和工作区启动耗时；
- judge 执行耗时；
- 通过、失败、超时和资源超限计数；
- Docker Engine 不可用和运行时库存指标；
- task、instance、execution_run、container、日志之间的 trace 关联；
- 管理端运行时库存和孤儿资源摘要。

验收重点：日志不包含密码、Token、Cookie、签名 URL 和完整源码；Docker Engine 停止时能定位到具体任务和 trace。

下一任务输入：指标名、日志字段、告警条件和 trace 查询方式。

### T10：P14-L 本地 Docker 真运行时

这是本地真实执行阶段，不是正式生产验收。

后端：

- 实现 `DockerLocalAdapter`；
- 创建学生专属工作区容器；
- 以 managed labels 标识容器；
- 设置 CPU、内存、进程数、TTL 和健康探针；
- 通过内部网络返回 `tasks.<service_name>:8080`；
- 实现一次性 judge 容器执行算法。

运行时镜像：

- 新增 `runtime/algorithm-workspace`；
- 提供 `/healthz`、`/webide/`、`/terminal/`、`/preview/`；
- 第一版使用外层实验草稿作为单文件编辑器；
- 后续再替换为 code-server 或 JupyterLab。

安全要求：

- 非 root；
- `read_only` 根文件系统；
- `cap_drop=ALL`；
- `no-new-privileges`；
- judge 使用 `network=none`；
- 不发布宿主机端口；
- 运行完成或超时后销毁 judge 容器。

验收重点：正确、错误、超时、内存超限、跨学生访问、容器过期回收和完整报告审核 E2E。

下一任务输入：本地容器镜像 digest、Compose 配置、runtime 网络和本地 E2E 证据。

### T11：P14-S 服务器真实适配

本地通过后再部署服务器：

- 使用已有 `DockerSwarmAdapter`；
- 接入私有镜像仓库和 digest；
- 配置 overlay 网络、节点标签、Secrets 和 Configs；
- 验证幂等创建、销毁、TTL、回滚和孤儿回收；
- 验证三 Manager quorum、节点故障、恢复、容量和性能。

服务器阶段不得修改学生任务、工作区、报告和审核 API，只替换运行时适配器、网络、镜像和调度配置。

## 四、统一出口条件

每个阶段必须同时记录：

- 本地 Compose 或真实环境；
- 本地门禁状态；
- 真实环境门禁状态；
- migration、OpenAPI 和镜像版本；
- 变更文件和 seed 命令；
- 正常、越权、幂等、并发、失败、恢复测试；
- 已知限制和明确阻塞项；
- 下一阶段可直接使用的 ID、接口和配置。

未填出口记录、未记录测试数量或仍有未解释失败时，不得进入下一阶段。

## 五、明确不做

- 不删除 P07 FakeRuntime；
- 不把本地单机 Docker 结果写成正式生产通过；
- 不让 Django Web 直接访问 Docker Socket；
- 不允许学生提交任意 shell 命令；
- 不通过放开网络、特权或宿主机端口解决执行问题；
- 第一版不同时支持多文件项目、任意语言和 VM 运行时。
